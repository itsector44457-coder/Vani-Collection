## Backend model and API design

The Reel model follows established project patterns with proper field types, validation, and indexes. The schema includes all necessary fields for managing video content: title and description for metadata, videoUrl and thumbnailUrl for media assets, productId reference for product linking, position for ordering, and isActive for soft deletion. The model includes proper audit fields (createdBy/updatedBy) and uses optimistic concurrency control to prevent race conditions during updates.

The API routes implement standard CRUD operations with proper middleware layering. All routes require authentication and catalog_manager/admin/super_admin roles through the requireRoles middleware. The routes use zod validation schemas that follow the project's pattern from content.js, providing structured error responses for malformed requests. Audit logging captures all admin operations for compliance tracking.

**confirmed** The GET endpoint supports pagination and filtering by isActive status, productId, and title search. The implementation properly handles edge cases like invalid page numbers and limits query results to prevent performance issues.

## Authentication and authorization patterns

The backend routes properly implement the project's authentication middleware stack. All reel admin endpoints require valid authentication through the auth middleware, followed by role-based access control requiring catalog_manager, admin, or super_admin privileges. This matches the pattern used by other admin resources and ensures only authorized staff can manage reels.

**confirmed** The audit middleware logs all create, update, and delete operations with proper actor tracking. The implementation includes the user ID in createdBy and updatedBy fields, maintaining a complete audit trail.

However, **confirmed** the frontend page itself has no role-based protection. While the API endpoints are properly protected, a user could potentially access the /admin/reels page directly if they bypass the navigation. The page would fail when making API calls, but this creates a poor user experience.

The admin reels page follows established patterns from the products admin page. The implementation uses the same UI components (PageHeading, Card, Modal, FilterTabs) and follows the same layout structure. The page includes comprehensive CRUD functionality with search filtering, status toggles, and modal-based editing forms.

**confirmed** The ReelsView component properly integrates with the useApiResource hook and provides demo data fallback when the API is unavailable. This matches the pattern used by other admin pages and ensures the interface remains functional during development.

The TypeScript interfaces (AdminReel, ReelInput) follow the project's naming conventions and provide proper type safety. The API client functions are properly integrated into the existing api-client.ts structure.

The API responses include populated product data (name, slug, images) which provides the frontend with sufficient information for display purposes.
